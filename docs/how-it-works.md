# Visitor Guide And Diagrams

[HOW_IT_WORKS.md](../HOW_IT_WORKS.md) and its diagrams are generated by the project-owned renderer
[`crates/tools/how-it-works`](../crates/tools/how-it-works/src/main.rs). This page records the visual grammar the
diagrams follow, which source owns what, and how to change a diagram.

## Commands

```bash
cargo run --locked -p how-it-works               # regenerate HOW_IT_WORKS.md and docs/assets/how-it-works/*.svg
cargo run --locked -p how-it-works -- --check    # fail if a committed output differs from what the seeds produce
```

Both commands first check the crate-map seed against the workspace (see [Source ownership](#source-ownership)) and
validate every diagram against the grammar below; either failure stops before anything is written. CI runs the
`--check` form. Regeneration rewrites only files whose content changed and removes SVGs in `docs/assets/how-it-works/`
that no diagram produces any more.

## What the diagrams are for

The diagrams are static reading aids for a visitor scrolling through the guide in GitHub's light or dark theme. A reader
should notice the major groups first, then pick one card and follow its relationships without first reading every
label.

- The overview must stay legible before any card text is read, and closer reading must reward it: labels and
  relationships are exact, not suggestive.
- Position carries meaning. A row, column or lane has a domain reason: dependency direction in the crate map, step
  order in the processing flow, time in the call timeline.
- Emphasis is earned by information. There are no decorative numerals, curves, slogans, gradients or shadows.

## Stable grammar

- **Cards** are flat rectangles whose surface stays distinct from the canvas in both themes. A narrow left bar carries
  the accent: primary for the subject of the diagram, secondary for context such as external dependencies. A small
  monospaced label in capitals names the role or position, the bold title states the meaning, and details and meta
  lines stay quieter.
- **Text** stays inside its card with a deliberate right margin, judged by a conservative width estimate, and the last
  detail line keeps a visible gap above the meta lines. The quietest text must stay readable at GitHub's content width
  (about 880 CSS px) without zoom; when a card gets crowded, rephrase or resize it instead of shrinking the type.
  Card, section and connector labels are capitalized when drawn, so keep unit symbols and Greek letters out of them
  (`s` would read as `S`, `μ` as `Μ`).
- **Text is painted after geometry.** Free-standing text (section headings, connector labels, notes) carries a
  canvas-colored halo so that no grid line, guide, connector or border can consume a glyph.
- **Connectors** are semantic, not decoration: horizontal and vertical segments only, soft elbows where a route turns,
  a straight approach before every filled arrowhead, and ends on the middle region of a card edge, never a corner. A
  route keeps a clearance corridor around every card it does not start or end at. Dashed connectors mark a conditional
  relationship: an optional dependency, or calibration frames skipping steps. Distinct relationships use distinct
  ports, and a short note is preferred to a long detour.
- **Canvas.** Both themes draw a 24 px square grid and a thin outer frame. The day canvas is warm paper; the night
  canvas is muted navy chosen against GitHub's dark surface. In the day palette section guides are stronger than the
  grid; the night palette, inherited unchanged, draws them fainter than its grid, so at night the section headings
  carry the grouping.
- **Design width.** Every diagram is 880 units wide, so one SVG unit is one CSS pixel at GitHub's content width and the
  12 px text renders at 12 px.

The validator in `src/validate.rs` enforces the mechanical part of this grammar: cards and canvas text inside the
canvas, card text fitting its height and keeping its right margin, orthogonal routes without zero-length segments, a
straight approach before arrowheads, stable ports, and clearance from unrelated cards. Legibility, emphasis and
routing quality are checked by rendering and looking (see [Updating a diagram](#updating-a-diagram)).

## Source ownership

| Source | Owns |
| --- | --- |
| `src/model.rs` | The primitives (cards, sections, guides, connectors, notes) and the named day and night palettes |
| `src/layout.rs` | The shared geometry: text positions inside cards, width estimates, port margin, elbow radius, clearance |
| `src/validate.rs` | The mechanical grammar rules |
| `src/svg.rs` | SVG output; it receives one complete palette, so day and night differ only in palette values |
| `src/diagrams/crate_map.rs` | The crate-map seed (`WORKSPACE_CRATES`, the Go reference pin, the Go package's module path and the crate it links) and its composition |
| `src/diagrams/processing_flow.rs` | The processing-flow composition, following the stage order of `CallEnhancer` |
| `src/diagrams/call_timeline.rs` | The call-timeline composition, following the timing contract of `ARCHITECTURE.md` |
| `src/manifest.rs` | The drift check between the crate-map seed, the Cargo manifests, `tools/go-parity/go.mod`, `go/go.mod`, the Go package's `#cgo LDFLAGS` and the diagram |
| `src/guide.rs` | The text of `HOW_IT_WORKS.md` |
| `src/outputs.rs` | Output paths, the freshness check and writing |

`HOW_IT_WORKS.md` and `docs/assets/how-it-works/*.svg` (day) and `*-dark.svg` (night) are generated projections. Never
edit them directly.

Compositions are authored: every coordinate is chosen by hand, and there is no layout engine. The crate map is the
only diagram with a machine-readable source of truth, so it is the only one checked mechanically against the code: a
crate, a normal dependency, an optional flag, the pinned Go reference, the Go package's module path or the static
library it links that differs between the seed, the manifests and the drawn cards and connectors fails generation and
`--check`. The manifest reader reads the keys of inline dependency tables exactly, so a feature or version string that
merely contains `path` or `optional = true` cannot change how a dependency is drawn. The processing flow and the call timeline restate
facts owned by `ARCHITECTURE.md` and `docs/algorithms.md`; review them against those pages whenever the stage order,
calibration or packet timing changes.

## Updating a diagram

1. Change the seed or composition in `src/diagrams/` (or the guide text in `src/guide.rs`) when the architecture, the
   stage order, the timing contract or a measured number changes. Change `src/model.rs`, `src/layout.rs` or
   `src/svg.rs` only when the shared visual language changes; a theme must never carry different content, layout or
   emphasis.
2. Run `cargo run --locked -p how-it-works`. A validation error names the diagram, the card or connector and the rule.
3. Render every changed SVG in both themes at 880 px and look at it, for example with
   `rsvg-convert -w 880 docs/assets/how-it-works/crate-map-dark.svg -o /tmp/crate-map-dark.png` or a browser. Check that
   the quietest text is readable, no text touches a route or border, every connector meets its card edge, and the
   night version is as legible as the day version. `rsvg-convert` and browsers are verification aids only, never project
   dependencies.
4. Run `cargo run --locked -p how-it-works -- --check` and the workspace gates, then commit the seeds and the generated
   files together.

Revisit the grammar when a real diagram cannot express an accurate relationship without breaking it. Do not weaken a
rule only to keep an existing placement.
